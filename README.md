# 扫码班报分位口径核对

班报只保留各终端在**共用、互不重叠的整数毫秒闭区间**上的分档笔数，以及 P50、P95、
总耗时三个汇总值。本服务用整数容量约束（**不按总笔数逐笔展开**）判断班报数字分别
能否在两种取位口径下由**同一组读数**复算，并给出可独立复算的「耗时 → 笔数」见证分布。

## 口径定义

设 `p` 为分位比例、`N` 为总笔数：

| 口径 | 取排序后第几项 |
| --- | --- |
| `ceil` | 第 `⌈pN⌉` 项（至少第 1 项） |
| `floor` | 第 `⌊pN⌋` 项（至少第 1 项） |

分位数条件「第 k 项 = q」等价于双侧容量约束：

- 小于 q 的笔数 ≤ k−1
- 大于 q 的笔数 ≤ N−k

同一口径下，P50、P95、总耗时必须由**同一组读数**同时满足。

## 算法（复杂度只与分档/阈值数有关，与总笔数无关）

1. 已提交明细作为固定读数；其余读数在所属分档 `[lo, hi]` 内自由取值。
2. 最小可行和：自由读数全部取 `lo`，再按最小提价贪心把读数批量上提到分位阈值，
   修复「小于 q」容量，并复验「大于 q」容量。
3. 最大可行和：对读数取负 `x = −v` 后复用同一过程。
4. 可行总耗时是最小和与最大和之间的全部连续整数（整数容量流多面体的连通性）。
5. 班报总耗时落在区间内时，在最小和基线上用带容量余量的**批量上提**构造见证分布，
   并独立复算总和、笔数、两个分位位置后才返回。

分档笔数即使达到 10^12 也只产生常数级分组，见证分布行数远小于总笔数。

## API（启动后访问 `/docs` 可交互演示）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `PUT` `/shifts/{shift_id}/report` | 登记/覆盖一班：分档、各终端档内笔数、P50/P95/总耗时；覆盖即换档，自动重映射明细 |
| `POST` `/shifts/{shift_id}/details` | 提交/更正终端明细，主键 `(终端, 流水号)`，同号即更正 |
| `GET` `/shifts/{shift_id}/details` | 查询已提交明细 |
| `POST` `/shifts/{shift_id}/check` | 用同一份已提交明细分别核对两种口径 |
| `GET` `/health` | 健康检查 |

明细提交规则：

- 耗时必须落在该终端该分档的闭区间内，否则整批退回（422，不落库）；
- `(终端, 分档)` 必须在班报中声明，且提交后档内笔数不得超过班报笔数，否则整批退回；
- 同 `(终端, 流水号)` 再次提交即为更正，可改值也可改到本终端已声明的其他分档。

### 班报换档（PUT 覆盖）更正规则

覆盖一份**已有明细**的班报时，服务在**同一数据库事务**内完成换档：

1. 每笔已有明细按其**实际耗时**归入本终端在新班报中的分档，
   流水号 `seq` 与耗时 `value_ms` 原样保留，仅改写 `bucket_idx`
   （分档互不重叠，一个耗时至多落入一个闭区间）；
2. 任一笔明细在新班报中找不到可落入的分档、或新班报未声明该终端对应档，
   即收集为错误；
3. 某终端归入某一新档的明细笔数超过新班报所报 `count`，同样收集为错误；
4. 出现任一错误则**整次更正退回**（HTTP 422，`detail.rejected=true`）：
   班报与明细都保持上一已提交状态，可继续用原班报核对、补交；
5. 全部通过才提交新班报并改写明细档号，响应返回
   `details_remapped`、`bucket_idx_changed` 与按 `(终端, 新档)` 的归入汇总。

换档与补交交错时：两类写操作由同一把锁串行化，每个事务都在单次加锁内
完成「读当前班报+明细 → 校验 → 落库」。因此换档必然纳入此前已接收的全部
明细；补交始终按**提交生效时**的班报整批校验，不会读到半更新状态。

### `/check` 的快照语义

`/check` 在单次加锁内取出班报与明细的**同一已提交快照**，随后的求解在锁外
进行——求解期间同班仍可继续补交/换档，但本次核对自始至终只针对该快照，
班报与明细不会串档。状态不一致（如明细档号越界、耗时不在档区间、档内超笔数）
统一以 422 返回错误原因，不再抛 500。

`/check` 响应中每个口径包含：`feasible`、不可行原因、可行总耗时区间
`feasible_sum_range_ms`，以及可行时的见证 `witness`（全局 `distribution`、
累计 `cumulative`、分终端 `by_terminal`、分位位置 `positions`）。

## Docker Compose 启动

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000/docs
```

在 `/docs` 页面可依次演示：

1. `PUT /shifts/{id}/report` 登记班报；
2. `POST /shifts/{id}/details` 补交明细，再 `GET .../details` 查明细；
3. `POST /shifts/{id}/check` 核对两种取位口径；
4. 再次 `PUT .../report` 提交仅对调两个分档区间（终端档号同步对调）的班报，
   响应中的 `bucket_idx_changed` 显示换档明细数；`GET .../details` 可见
   流水号与耗时不变、档号已按耗时迁入新档；
5. 提交一份让某笔明细无处落档的班报，得到 422 整次退回，
   重新查明细与 `/check`，确认原班报、原明细仍在生效。

SQLite 数据保存在命名卷 `shift_data`（容器内 `/data/shift.db`）。

## 自测结果

- `tests/test_solver_brute.py`：对 16 组小场景（含固定明细）枚举**全部读数组合**
  逐笔排序，与求解器在每一个候选总耗时上的可行性结论逐一对照，全部一致；
  另含 10^12 笔大档测试，见证分布仍为常数行。
- `tests/test_api.py`：端到端覆盖
  1. 两种口径均可行且见证可独立复算；
  2. 越界/未声明终端/超档内容量均整批退回且不落库；
  3. 明细更正后核对结论发生变化（更正前两口径均可行，更正后 `ceil` 失效、
     `floor` 仍可行），再更正回退后结论恢复；
  4. 60 亿/40 亿/20 亿笔大档，见证为聚合分布、不逐笔展开；
  5. `/docs`、`/health` 可访问。
- `tests/test_remap.py`：换档更正专项，共 7 个用例，覆盖
  1. **换序**：仅对调两个分档，已有明细按实际耗时迁入本终端新档，
     流水号/耗时原样保留，未涉及的档号不变；
  2. **退回（找不到新档）**：某笔耗时落不进任何新档区间时整次 422，
     班报与明细维持原状，原班报下 `/check` 与补交照常工作；
  3. **退回（超班报笔数）**：归入某终端某档的明细多于班报所报笔数时
     整次 422，错误体带 `remapped/capacity` 对照；
  4. **换档/补交交错**：换档纳入此前全部明细；换档后用旧档号补交被
     生效班报整批退回，整批中任一条非法则整批不落库；
  5. **并发**：多线程并发换档（来回切换）、补交、`/check` 共 120+ 次混合调用，
     无异常、无 500，最终状态档号/耗时/班报完全自洽；
  6. **快照核对**：补交持续进行期间连续 `/check`，每次响应内部自洽、
     恒为 200（求解期间同班仍可补交）。
